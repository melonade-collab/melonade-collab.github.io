Integration Adapter Hub

Customer data arrives in one shape. Every downstream system expects a different one. This demo shows intake, transformation, and adapter routing — the three layers that make integrations actually work.

Problem

▼

Every integration project hits the same wall: data collected from a customer comes in one shape, but ServiceNow expects an incident record, Salesforce wants a Case object, and the analytics pipeline wants flat JSON. Without an adapter layer, teams either write one-off transformations for each system or hand the data over unformatted and let the receiving team figure it out.

The deeper problem: this logic is invisible. It lives in custom scripts, tribal knowledge, and Slack threads. When someone asks "what does billing actually receive when a customer submits a complaint?" no one can easily answer. This demo makes the transformation layer explicit and explorable.

Tech

▼
  • Pure client-side JavaScript — no backend, no API calls, no framework
  • Intent classifier reads the issue description and maps to one of five categories (billing, shipping, technical, complaint, general)
  • Four adapter formatters transform the same raw input into ServiceNow incident, Salesforce Case, JSON webhook, and CSV — each with system-appropriate field names and structure
  • A "sample data" button pre-fills a realistic fictional submission to demonstrate the flow without the user having to type
  • Syntax highlighting applied client-side via regex replacements on serialized JSON

Features

▼
  • Intake form collects name, email, account ID, and freeform issue description — the same inputs any real support form would capture
  • Brief processing animation makes the transformation step visible rather than instant, showing intake → format → route
  • Adapter tabs let you switch destinations: ServiceNow, Salesforce, JSON Webhook, CSV row — same data, four different shapes
  • A "Connected" indicator on each active adapter reinforces the plug-in metaphor
  • Intent detection dynamically changes the category field in each output format based on what the user actually wrote

Why This

▼

Integration work is hard to make legible to stakeholders — it's all plumbing. A PM who owns this space needs to show they understand not just that data needs to move, but that the same event looks completely different depending on where it's going and why. The adapter metaphor is the PM's mental model made visible: you plug in a destination, the system handles the shape. That's the product decision.
