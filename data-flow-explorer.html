Integration Adapter Hub

Customer data arrives in one shape. Every downstream system expects a different one. This demo shows all four layers: intake, normalization, adapter formatting, and what the agent sees on the other end.

Problem

▼

Every integration project hits the same wall: data collected from a customer comes in one shape, but ServiceNow expects an incident record, Salesforce wants a Case object, and the analytics pipeline wants flat JSON. Without an adapter layer, teams either write one-off transformations for each system or hand the data over unformatted and let the receiving team figure it out.

The deeper problem: this logic is invisible. It lives in custom scripts, tribal knowledge, and Slack threads. When someone asks "what does billing actually receive when a customer submits a complaint?" no one can easily answer. This demo makes the transformation layer explicit and explorable — all the way through to what an agent sees on the other end.

Tech

▼
  • Pure client-side JavaScript — no backend, no API calls, no framework
  • Intent classifier reads the issue description and maps to one of five categories (billing, shipping, technical, complaint, general)
  • A normalization step produces a canonical internal record before any adapter sees the data — mirroring how a real integration hub works
  • Five adapter formatters (ServiceNow, Salesforce, JSON webhook, CSV, Email) each produce system-appropriate output from the same canonical record
  • Step 4 renders a mock of the receiving system's UI — showing what a frontline agent actually sees after the data arrives

Features

▼
  • Four visible steps on screen: intake form → normalized canonical record → adapter output → agent-facing system view
  • Step 4 system mocks update live when you switch adapters — same data, different interface
  • ServiceNow and Salesforce mocks use system-appropriate field vocabulary and visual chrome
  • Email adapter shows a formatted notification as a support team inbox would receive it
  • CSV adapter shows a spreadsheet table with the data row highlighted
  • Intent detection dynamically sets category, routing team, and SLA hours based on what the customer actually wrote

Why This

▼

Integration work is hard to make legible to stakeholders — it's all plumbing. A PM who owns this space needs to show they understand not just that data needs to move, but that the same event looks completely different depending on where it's going and why. Step 4 is the closer: it shows the human at the end of the pipeline. That's who integrations are actually for.
